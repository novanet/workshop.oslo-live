Sjekkpunkt 1 · lokalt, uten levering

Lab 1: Bygg pipelinen

Koble sammen delene fra GitHub-issue til pull request i Pipeline.cs, men test bare lokalt. Du får ferdige komponenter og en oppskrift, men skriver selv rekkefølgen.

MålEn pipeline som er klar for Azure.
ArbeidsstedDitt eget repo og din lokale devcontainer.
Ferdig nårRunStages bygger grønt og dry-run er ren.

Før du begynner

Ha dette klart før du begynner:

  • Et eget privat repo for agenten din.
  • Et klassisk GitHub-token med bare public_repo, og godtatt collaborator-invitasjon til novanet/workshop.oslo-live. Lab 1 bruker det bare i lesende dry-run; Lab 2 skriver med det. Fine-grained funker ikke for collaborators utenfor Novanet-orgen.
  • En ANTHROPIC_API_KEY fra kurslederen. Du skal normalt ikke betale selv; Claude.ai-abonnement og Anthropic API-betaling er separate. Zip-filen har kursets ANTHROPIC_WORKSPACE_ID som standard, og workeren bruker den også som fallback hvis en eldre .env-fil mangler variabelen.
  • En kopi av mini-nils.zip, pakket ut i mappen der du skal jobbe.
  • En devcontainer eller Codespace med .NET 10, gh og Claude Code.

Agenten endrer ikke sitt eget repo. Den vil senere klone øvingsrepoet, lage en branch der og åpne pull requesten fra Azure. I Lab 1 skal ingen lokal kjøring reservere issue, skrive kommentarer, pushe eller opprette PR.

Lag agentrepoet

git init -b main
git add -A
git commit -m "Start fra delene til Mini-Nils"
gh repo create mini-kari --private --source . --push

Bytt kari med navnet ditt.

Fyll inn miljøet

cp .env.example .env
AGENT_NAME=litj-nils
GH_TOKEN=ghp_...
ANTHROPIC_API_KEY=sk-ant-...

Tokenet trenger bare public_repo. Feilen addComment eller replaceActorsForAssignable i Lab 2 betyr ofte at du ikke har godtatt collaborator-invitasjonen til øvingsrepoet. Hvis workeren sier Mangler eller ikke utfylt: ANTHROPIC_API_KEY, må du be kurslederen om Claude-nøkkelen og legge den i .env. Hvis Claude fortsatt sier at nøkkelen ikke er scoped til et workspace, må du hente den nyeste mini-nils.zip eller oppdatere worker-koden og kontrollere at loggen sier at Anthropic workspace-ID er satt. --dry-run kan kjøres uten Anthropic-nøkkel.

Sjekk verktøyene

dotnet --version
gh --version
claude --version
dotnet build

Bruk devcontainer eller Codespaces hvis noe mangler. På Windows kan du installere Claude Code med npm install -g @anthropic-ai/claude-code.

Sjekk oppsettet først

Sjekk at issuen er tilgjengelig uten å klone repoet, bruke modellkall eller skrive noe til GitHub.

dotnet run --project src/Worker -- `
  --issue 1 `
  --repo novanet/workshop.oslo-live `
  --dry-run

--dry-run leser issue-status og stopper før reservasjon, clone, issue-kommentar, Claude Code, commit og PR. Direkte issue-kjøring uten --dry-run er blokkert i starter-kitet. Først når agenten er deployet og webhooken leverer en kømelding, kan den reservere issue, kommentere og opprette PR. Dry-run krever ikke ANTHROPIC_API_KEY og kan bare brukes med --issue og --repo, ikke kømodus.

Betaling feilet?Du skal normalt ikke kjøpe API-kreditt selv. Be kurslederen om nøkkelen fra kursets Anthropic-workspace. Claude.ai-abonnementet gir ikke automatisk API-kreditt.

Start med skjelettet

Scriptet legger inn en skjelettfil med den ytterste Run-metoden og hjelpeklassene du trenger. RunStages er din oppgave.

python setup-lab1.py
dotnet build

Det som stod der fra før lagres i .kurs/Pipeline.forsok.cs. Ikke åpne sjekkpunktet ennå; det er den ferdige løsningen som skal brukes hvis du faller av.

Slik gjør du det i RunStages

Ta ett steg om gangen. Kjør dotnet build etter hvert steg. Oppskriften beskriver hva som skal skje, men ikke C#-løsningen.

1

Issue-status · før modellen

Kontroller at issuen er åpen

Når workeren kjører fra Azure, kaller du Reservation.IsBusy(task, AgentName). Ved lukket issue kommenterer du og returnerer 0; ellers kaller du Reservation.Claim(task). Tildelingen er synlig, ikke eksklusiv: flere deltakere kan jobbe parallelt, og første mergete PR vinner.

2

Arbeidsområde

Klon repoet og lag branch

Kall Repository.Clone(task.Repo, workspace), lag task.BranchName med CreateBranch, logg repo.Path og kommenter StartMarker(task). Modellen skal aldri jobbe direkte på main.

3

Kontekst

Bygg systemprompt og kontekst

Kall InstallSkills(), ReadMemory() og BuildSystemPrompt(memory). Start previousOutput som en tom streng. Regler, konvensjoner og hukommelse skal være lesbar input.

4

Modellsteg

Kjør config.Stages

For hvert steg velger du stage.Model eller config.Model, bygger prompt med BuildPrompt, kaller ClaudeRunner.Run, legger resultatet i runs og logger LogUsage. Starter-kitet viser research, plan review, implement og self-review med ulike Claude-modeller. Deretter gjør workeren bygg, test og levering. Ved feil kommenterer du, bruker EndMarker og returnerer 1.

5

Endring · ingen tom PR

Sjekk at det finnes en endring

Kall repo.HasChanges(). Ved tom diff kommenterer du siste svar, husker utfallet med Remember, legger ved forbruk og returnerer 0.

6

Verifisering

Kjør bygg og test

Kall Verify(repo.Path). Når verifiseringen feiler og StopOnVerifyFailure er sann, kommenterer du verifyLog, husker utfallet og returnerer 2 uten PR.

7

Leveranse

Lever endringen

Kall CommitAndPush, bygg PR-teksten med PrBody og kall CreatePullRequest når workeren kjører fra Azure-køen. Bruk utkast når verifiseringen er rød, og aktiver auto-merge bare når den er grønn. Skriv sammendrag og husk utfallet.

Nå sjekkpunkt 1

dotnet build
dotnet run --project src/Worker -- `
  --issue 1 `
  --repo novanet/workshop.oslo-live `
  --dry-run

Dry-run bekrefter at issue og token er tilgjengelige, men skriver ikke assignee, kommentar, branch, commit eller PR. Den første virkelige kjøringen skal komme fra Azure etter at webhooken er koblet til.

Sjekkpunkt 1Din egen implementasjon av RunStages bygger grønt, dry-run er ren, og du kan forklare hvor workeren senere reserverer issue, kommenterer og leverer PR.

Hvis du trenger hjelp

Forsøket ditt blir tatt vare på før den ferdige løsningen kopieres inn:

./sjekkpunkt.sh lab1
dotnet build

I PowerShell kan du se forskjellen slik:

code --diff .kurs\Pipeline.forsok.cs src\Worker\Pipeline.cs
RedningsnettLes den ferdige pipelinen etterpå og finn ut hvilket steg du manglet før du går videre til Lab 2.

Hvis du blir tidlig ferdig

  • Flytt en kontroll og forklar hvorfor den fortsatt skjer på samme måte.
  • Endre hva som skjer når verifisering feiler.
  • Logg en ekstra måling i PR-rapporten.
  • Gi et modellsteg mindre verktøytilgang.

Dokumenter hva som ble bedre, hva som ble dårligere og hvilken måling som viser forskjellen.
