Lab 1: Monter agenten

Kjør en fungerende baseline fra GitHub-issue til pull request, les orkestreringen og gjør én bevisst policyendring. Du skal ikke bruke labtid på å kopiere store kodeblokker.

MålEn agent som lager en reviewbar PR.
ArbeidsstedDitt eget repo og din lokale devcontainer.
Ferdig nårBaselinen har kjørt, og du kan forklare policyendringen din.

Før du begynner

Ha dette klart før du begynner:

  • Et eget privat repo for agenten din.
  • Skrivetilgang til novanet/workshop.oslo-live via et GitHub-token med Contents, Issues og Pull requests med read/write.
  • En kopi av mini-nils.zip, pakket ut i mappen der du skal jobbe.
  • En devcontainer eller Codespace med .NET 10, gh og Claude Code.

Agenten endrer ikke sitt eget repo. Den kloner øvingsrepoet, lager en branch der og åpner pull requesten der.

Lag agentrepoet

git init -b main
git add -A
git commit -m "Start fra delene til Mini-Nils"
gh repo create mini-kari --private --source . --push

Bytt kari med navnet ditt.

Fyll inn miljøet

cp .env.example .env
AGENT_NAME=Mini-Kari
GH_TOKEN=github_pat_...
ANTHROPIC_API_KEY=sk-ant-...

Tokenet trenger Contents, Issues og Pull requests med read/write på øvingsrepoet.

Sjekk verktøyene

dotnet --version
gh --version
claude --version
dotnet build

Bruk devcontainer eller Codespaces hvis noe mangler.

Monter baseline med et script

Det er unødvendig å bruke labtid på å kopiere rundt 100 linjer med orkestreringskode. Scriptet installerer baselinen og tar vare på det som stod der fra før.

    python setup-lab1.py
dotnet build

Baselinen legges i src/Worker/Pipeline.cs. Det forrige forsøket ligger i .kurs/Pipeline.forsok.cs. Åpne pipeline-filen og les gjennom disse sju kontrollene:

1. Reservasjon

Reservation.IsBusy og Reservation.Claim hindrer kollisjoner. --force er et eksplisitt unntak.

2. Arbeidsområde

Repoet klones og får en egen branch. Modellen jobber aldri direkte på main.

3. Kontekst

Systemregler, skills og minne er eksplisitt input som kan leses og versjoneres.

4. Modellsteg

Hvert steg får prompt, modell, verktøy og budsjett fra konfigurasjonen.

5. Endringskontroll

En god tekst uten diff blir ikke til en tom pull request.

6. Verifisering

Bygg og test kjøres utenfor modellen og kan stoppe leveransen.

7. Levering

Branchen committes, pushes og leveres som en reviewbar pull request.

Gjør én bevisst endring

Velg én policy, endre bare den, bygg og kjør på nytt. Skriv ned forventningen din før du starter.

  • Sett stopOnVerifyFailure til true i agent/stages.json.
  • Reduser maxTurns for ett modellsteg.
  • Bytt modell for ett steg.
  • Fjern ett verktøy fra allowedTools.

Sammenlign logg, diff, tokenforbruk og tid med baselinen. Da ser du forskjellen mellom kode som styrer flyten og modellen som gjør selve kodeendringen.

Kjør og nå sjekkpunktet

dotnet run --project src/Worker -- `
  --issue 1 `
  --repo novanet/workshop.oslo-live `
  --force

På macOS/Linux kan du bruke \ i stedet for PowerShells linjefortsettelse. Følg loggen: oppgaven hentes, repoet klones, modellen kjører, bygg/test kjøres og PR-adressen skrives ut.

Sjekkpunkt 1Baselinen har åpnet en PR, du har dokumentert én policyendring, og du kan peke på hva som er deterministisk kode og hvor modellen brukes.

Hvis du faller av

Scriptet tar vare på forsøket ditt før baselinen kopieres inn:

    python setup-lab1.py
dotnet build

Det gamle aliaset fungerer også i Bash:

./sjekkpunkt.sh lab1

I PowerShell kan du se forskjellen mellom forsøket og baselinen slik:

code --diff .kurs\Pipeline.forsok.cs src\Worker\Pipeline.cs
Ikke skjul feilenLes gjerne diffen i forsøket ditt etterpå. Scriptet er et redningsnett, ikke en erstatning for å forstå rekkefølgen.

Hvis man blir tidlig ferdig

  • Gjør stopOnVerifyFailure strengere eller mer ettergivende.
  • Gi implementeringssteget færre turer.
  • Tillat ett ekstra verktøy og vurder om det faktisk hjelper.

Sammenlign med baselinen og dokumenter hva som ble bedre, hva som ble dårligere og hvilken måling som viser forskjellen.
