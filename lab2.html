Før du starter

Lab 2 bygger på det du gjorde før lunsj. Kryss av dette:

  • Sjekkpunkt 1 er nådd: RunStages bygger grønt, eller du har kjørt ./sjekkpunkt.ps1 lab1, og første deploy fra Actions er grønn.
  • Du har Receiver URL og Issue label fra Actions → Summary. Med AGENT_NAME=kari er etiketten kari.
  • Kurslederen har koblet webhooken din til Oslo Live i lunsjen.
Første virkelige kjøringLab 1 var lokal og skrivebeskyttet. Ikke opprett PR, skriv kommentar eller tildel issue manuelt. Nå er det Azure-workeren som tildeler issue, skriver kommentarer og oppretter PR.

Dette kjører i Azure

Receiver

En Container App som validerer webhook-signaturen og legger en melding i Storage Queue. Under kurset har den minReplicas: 1, så GitHub ikke venter på kaldstart. GitHub gir opp etter 10 sekunder.

Queue

Storage Queue holder oppgaven til KEDA ser meldingen og starter en worker-kjøring.

Worker

En Container Apps Job som skalerer til null. Den kloner repoet, kjører claude -p, bygger, tester og åpner PR.

Konfigurasjon

GitHub Actions logget inn med AZURE_CREDENTIALS og sendte GH_TOKEN, ANTHROPIC_API_KEY og WEBHOOK_SECRET secure til deployen.

Viktig skilleIssuen og PR-en bor i fellesrepoet. Receiver, worker og kø ligger i kursets felles ressursgruppe, med unike navn avledet fra AGENT_NAME. Container Registryet er felles for kurset, men bildene ligger under mini-nils/kari/, slik at deltakerne ikke overskriver hverandre. Receiver og worker godtar bare TARGET_REPO, som er novanet/workshop.oslo-live.

Hva er Actions Summary og KEDA?

Les Actions Summary

Åpne den ferdige workflow-kjøringen og velg Summary. Der finner du Receiver URL, Issue label og Worker job. .deploy-outputs.json ligger bare på den midlertidige Actions-runneren og skal ikke forventes lokalt.

$ReceiverUrl = 'https://ca-...azurecontainerapps.io'

Kopier adressen fra sammendraget inn i terminalen.

KEDA starter jobben

KEDA betyr Kubernetes Event-driven Autoscaling. Azure Container Apps bruker KEDA til å følge med på antall meldinger i Storage Queue og starte Container Apps Job når køen ikke er tom.

Jobben står normalt på null kjøringer. KEDA sjekker køen hvert 30. sekund, starter en kjøring når den finner en melding, og workeren henter én melding før den avslutter. Derfor er en liten forsinkelse normalt, og det finnes ingen worker som står og kjører hele tiden.

Følg verdiene i BicepminExecutions: 0 gir scale-to-zero, maxExecutions: 3 begrenser hvor mange kjøringer skalaen kan starte, og pollingInterval: 30 bestemmer hvor ofte KEDA sjekker køen. KEDA er ikke selve workeren; den er mekanismen som starter den.

Fra issue til PR i fem trinn

1

Mottaket

Sjekk at receiveren svarer

$ReceiverUrl = 'https://ca-...azurecontainerapps.io'
Invoke-RestMethod "$ReceiverUrl/"

Forvent: Mini-Nils receiver. Listening for the «kari» label. curl.exe "$ReceiverUrl/" gir det samme.

2

Trigger

Merk en issue med etiketten din

Åpne GitHub Issues og velg en av Feil 2 til 5 som ingen har tatt ennå. Sett etiketten fra Summary på den, i nettleseren eller slik:

gh issue edit 3 --repo novanet/workshop.oslo-live --add-label kari

Bytt 3 med issuen du valgte. Receiveren mottar alle hendelser, men sender bare dine videre. Ikke tildel issuen, skriv startkommentar eller opprett PR selv.

3

Mens du venter · 401

Test at mottaket avviser feil hemmelighet

$Body = '{"repo":"novanet/workshop.oslo-live","issueNumber":2}'
curl.exe -i -X POST "$ReceiverUrl/tasks" `
  -H "X-Webhook-Secret: deliberately-wrong" `
  -H "Content-Type: application/json" `
  --data-raw $Body

Forvent 401 Unauthorized. Dette starter ingen jobb. Finn kontrollen i src/Receiver/Program.cs. /tasks krever hemmeligheten i en header, og webhooken fra GitHub er signert med HMAC. Selve kømeldingen er ikke signert, så mottaket er porten.

4

Følg jobben

Les issue-kommentarene

gh issue view 3 --repo novanet/workshop.oslo-live --comments

KEDA sjekker køen hvert 30. sekund, så litt venting er normalt. Først kommer startkommentaren fra agenten, så sluttkommentaren med PR-adresse og forbrukstabell. Lukk laptopen mens jobben kjører. PR-en skal komme fra workeren i Azure, ikke fra terminalen din.

Worker-loggen i Azure kan kurslederen vise. Ved feilsøking kan kurslederen midlertidig sette CLAUDE_VERBOSE=true i env:-blokken øverst i .github/workflows/deploy-azure.yml før en ny kjøring. Sett verdien tilbake etterpå.

5

Pull request · sjekkpunkt

Les PR-en

gh pr list --repo novanet/workshop.oslo-live --author "@me"

Åpne PR-en og les rapporten og forbrukstabellen. Agenten merger ikke selv; PR-en venter på review fra et menneske. Var bygget rødt, er PR-en et utkast.

Sjekkpunkt 2En merket issue gir en pull request opprettet av Azure-jobben.

Se kostnaden i Log Analytics

Kurslederen kan vise dette i Azure-portalen. Workeren skriver en LLM request completed-linje for hver modellkjøring. Det er denne linjen som brukes i forbrukstabellen på PR-en og i Status.

ContainerAppConsoleLogs_CL
| where ContainerName_s == "worker"
| where Log_s contains "LLM request completed"
| project TimeGenerated, Log_s
| order by TimeGenerated desc

Hvis du blir tidlig ferdig

Gjør én liten endring i infra/main.bicep som krever ny deploy.

  • Endre pollingInterval i KEDA-regelen fra 30 til 15.
  • Commit og push til main. Deployen starter av seg selv i Actions.
  • Be kurslederen bekrefte den nye verdien i Azure.

Du ber KEDA sjekke køen oftere. Du endrer ikke hvordan workeren behandler meldingen.

Finn også i infra/main.bicep hvor KEDA-regelen står, hvor repository secrets blir til jobbens miljøvariabler, og hvorfor mottaket har minReplicas: 1 under kurset.

Hvis noe stopper

Webhooken når ikke fram

Ikke legg WEBHOOK_SECRET i terminalhistorikk eller del den i en issue. Be kurslederen kontrollere Recent deliveries og redelivere webhooken med kurslederens oppsett.

Deploy feiler på rettigheter

Kontroller at AZURE_CREDENTIALS finnes som repository secret og at AGENT_NAME er satt. Hvis feilen fortsetter, må kurslederen rette service-principalens roller.

Jobben feiler med en gang

Be kurslederen hente worker-loggen. Manglende miljøvariabler ligger vanligvis under env: i infra/main.bicep.
