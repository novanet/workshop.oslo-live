Lab 2: Til skyen

Deploy agenten slik at en merket GitHub-issue gir en pull request fra Azure, uten at laptopen din er med. Test mottaket og gjør én liten endring som krever ny deploy.

MålEn issue starter en jobb fra null i Azure.
ArbeidsstedKursets felles ressursgruppe og ACR, med din egen agent-identitet.
Ferdig nårPR-en er opprettet av Container Apps Job.

Før du starter

Lab 2 bygger på agenten du implementerte i Lab 1. Kryss av dette før du deployer:

  • Lab 1 er nådd, eller du har kjørt ./sjekkpunkt.sh lab1 og dotnet build er grønt.
  • Kurslederen gir deg AZURE_CREDENTIALS, GH_TOKEN, ANTHROPIC_API_KEY og WEBHOOK_SECRET. Du legger dem selv som repository secrets i agentrepoet ditt, og setter AGENT_NAME som repository variable.
  • AZURE_CREDENTIALS er et service-principal-JSON som GitHub Actions bruker. Du trenger ikke en personlig Azure-bruker med Contributor-tilgang for å deploye.
  • GH_TOKEN må ha Contents, Issues og Pull requests read/write, samt Metadata read-only, på akkurat novanet/workshop.oslo-live. Anthropic-nøkkelen kommer normalt fra kurslederen; du skal ikke betale selv.
  • Starter-kitet bruker kursets felles ressursgruppe, registry og pull-identitet automatisk. az er bare nødvendig hvis du har fått separat lesetilgang til Azure; curl holder for helsesjekken.
Første virkelige kjøringLab 1 var lokal og skrivebeskyttet. Ikke opprett PR, skriv kommentar eller tildel issue manuelt. Etter at webhooken er koblet til, er det Azure-workeren som tildeler issue, skriver kommentarer og oppretter PR.

Dette deployer du

Receiver

En Container App som validerer webhook-signaturen og legger en melding i Storage Queue. Den har minReplicas: 0.

Queue

Storage Queue holder oppgaven til KEDA ser meldingen og starter en worker-kjøring.

Worker

En Container Apps Job kloner repoet, kjører claude -p, bygger, tester og åpner PR.

Konfigurasjon

GitHub Actions logger inn med AZURE_CREDENTIALS og sender GH_TOKEN, ANTHROPIC_API_KEY og WEBHOOK_SECRET secure til deployen.

Viktig skilleIssuen og PR-en bor i fellesrepoet. Receiver, worker, kø og hemmeligheter ligger i kursets felles ressursgruppe, med unike navn avledet fra AGENT_NAME. Container Registryet er felles for kurset, men bildene ligger under mini-nils/<agent-label>/, slik at deltakerne ikke overskriver hverandre.

Hva er Actions Summary og KEDA?

Les Actions Summary

Åpne den ferdige workflow-kjøringen og velg Summary. Der finner du Receiver URL, Issue label og Worker job. .deploy-outputs.json ligger bare på den midlertidige Actions-runneren og skal ikke forventes lokalt.

RECEIVER_URL='https://ca-...azurecontainerapps.io'
WORKER_JOB_NAME='caj-...-worker'

Kopier verdiene fra sammendraget til terminalen når du skal teste mottaket eller følge jobben.

KEDA starter jobben

KEDA betyr Kubernetes Event-driven Autoscaling. Azure Container Apps bruker KEDA til å følge med på antall meldinger i Storage Queue og starte Container Apps Job når køen ikke er tom.

Jobben står normalt på null kjøringer. KEDA sjekker køen hvert 30. sekund, starter en kjøring når den finner en melding, og workeren henter én melding før den avslutter. Derfor er en liten forsinkelse normalt, og det finnes ingen worker som står og kjører hele tiden.

Følg verdiene i BicepminExecutions: 0 gir scale-to-zero, maxExecutions: 3 begrenser hvor mange kjøringer skalaen kan starte, og pollingInterval: 30 bestemmer hvor ofte KEDA sjekker køen. KEDA er ikke selve workeren; den er mekanismen som starter den.

Deploy i seks trinn

1

Repository settings

Gjør repoet klart for Actions

Kurslederen gir deg verdiene. Legg AZURE_CREDENTIALS, GH_TOKEN, ANTHROPIC_API_KEY og WEBHOOK_SECRET som repository secrets, og sett AGENT_NAME som repository variable.

AGENT_NAME=litj-nils
gh variable set AGENT_NAME --repo OWNER/REPO --body "$AGENT_NAME"

AZURE_CREDENTIALS brukes av azure/login@v2. Ikke kopier den til .env eller bruk den som lokal Azure-innlogging.

2

Deploy

Start workflowen

Push til main, eller åpne Actions → Build and deploy Mini-Nils → Run workflow. Workflowen logger inn med AZURE_CREDENTIALS, oppretter eller oppdaterer ressursene, bygger bildene i kursets felles ACR og deployer på nytt med de namespacede bildene.

Du skal ikke opprette eget ACR, kjøre deploy-skriptet lokalt, kjøre az login eller bruke docker login.

3

Actions Summary

Kontroller deployen

Åpne den ferdige workflow-kjøringen og velg Summary. Kopier Receiver URL, Issue label og Worker job derfra.

RECEIVER_URL='https://ca-...azurecontainerapps.io'
WORKER_JOB_NAME='caj-...-worker'
curl "$RECEIVER_URL/"

Forvent: Mini-Nils receiver. Listening for the «mini-kari» label. Output-filen .deploy-outputs.json ligger bare på Actions-runneren.

4

Webhook · kursleder

Be om kobling til Oslo Live

Du har ikke admin på fellesrepoet. Si fra når deployen er ferdig; kurslederen registrerer webhooken, lager etiketten og kobler URL-en til repoet.

Vil du aktivere svar på PR-mentions, sett AGENT_MENTION som repository variable. Bruk loginet som GH_TOKEN tilhører. Kurslederens webhook-skript registrerer de nødvendige kommentar- og review-hendelsene.

5

Trigger

Merk en issue med agentetiketten

Åpne GitHub Issues, velg en ledig oppgave kurslederen har anbefalt, og sett etiketten til navnet fra deployen. Receiveren mottar alle hendelser, men sender bare dine videre. Ikke tildel issue, skriv startkommentar eller opprett PR selv; workeren gjør dette fra Azure.

az containerapp job execution list -g rg-agentic-workshop `
  -n "$WORKER_JOB_NAME" -o table

KEDA sjekker køen hvert 30. sekund, så opptil 30 sekunders venting er normalt.

PR-mentionSkriv @github-loginet-ditt i en PR-kommentar eller inline review-kommentar. Agenten får kommentaren som en egen kømelding, leser PR-en uten å endre kode og svarer. Inline review-kommentarer får svar i samme tråd; en vanlig PR-kommentar får et nytt svar i PR-samtalen.
6

Logger · sjekkpunkt

Følg kjøringen og les loggen

az containerapp job logs show -g rg-agentic-workshop `
  -n "$WORKER_JOB_NAME" --container worker --follow

Lukk laptopen mens jobben kjører. PR-en skal komme fra workeren i Azure, ikke fra terminalen din.

Ved feilsøking kan kurslederen midlertidig sette CLAUDE_VERBOSE=true i env:-blokken øverst i .github/workflows/deploy-azure.yml før en ny kjøring. Sett verdien tilbake etterpå.

Deploy fra GitHub Actions

Starter-kitet inneholder en workflow som kan bygge og rulle ut fra deltakerrepoet, uten Docker lokalt. Applikasjonshemmelighetene ligger som repository secrets og brukes bare under deploy.

GitHub-innstillingNavnPåkrevdBruk
Repository variableAGENT_NAMEJaUnikt agentnavn, for eksempel litj-nils.
Repository variableAGENT_MENTIONNeiGitHub-login uten @ for mention-svar.
Repository variableCLAUDE_MODELNeiFallback-modell hvis stages.json ikke angir modell.
Repository secretAZURE_CREDENTIALSJaService-principalens komplette Azure-credentials-JSON.
Repository secretGH_TOKENJaFine-grained token med tilgang til novanet/workshop.oslo-live.
Repository secretANTHROPIC_API_KEYJaKurslederens Anthropic API-nøkkel.
Repository secretWEBHOOK_SECRETJaSamme verdi som brukes ved GitHub-webhooken.

Dette er hele listen. Du trenger ingen andre GitHub variables eller repository secrets for deploy.

1. Repository secrets

Legg GH_TOKEN, ANTHROPIC_API_KEY, WEBHOOK_SECRET og AZURE_CREDENTIALS som repository secrets i deltakerrepoet.

2. Bruk repository secret

Workflowen sender de tre applikasjonshemmelighetene som secure deploy-parametere. De lagres ikke i Key Vault, ACR eller image-lag.

3. Legg inn agent-identiteten

Sett bare AGENT_NAME som repository variable, for eksempel litj-nils. Ressursgruppe, Azure-suffiks og ACR-namespace avledes automatisk.

4. Start deployen

Push til main, eller åpne Actions → Build and deploy Mini-Nils → Run workflow og start den manuelt. Workflowen oppretter, bygger og deployer alt fra GitHub Actions.

Se kostnaden i Log Analytics

Workeren skriver en LLM request completed-linje for hver modellkjøring. Det er denne linjen som brukes i forbrukstabellen på PR-en og i Status.

ContainerAppConsoleLogs_CL
| where ContainerName_s == "worker"
| where Log_s contains "LLM request completed"
| project TimeGenerated, Log_s
| order by TimeGenerated desc

Feilsøk en kontrollert feil og deploy en endring

Test først at mottaket avviser en ugyldig intern kømelding. Dette skal ikke starte en jobb.

curl -i -X POST "$RECEIVER_URL/tasks" `
  -H "X-Webhook-Secret: deliberately-wrong" `
  -H "Content-Type: application/json" `
  -d '{"repo":"novanet/workshop.oslo-live","issueNumber":2}'

Forvent 401 Unauthorized. Finn kontrollen i src/Receiver/Program.cs og forklar hvorfor hemmeligheten ikke skal ligge i URL-en, kildekoden eller terminalhistorikken.

Gjør deretter én liten endring i infra/main.bicep:

  • Endre pollingInterval i KEDA-regelen fra 30 til 15.
  • Push endringen og start Actions → Build and deploy Mini-Nils → Run workflow for å bygge og rulle ut på nytt.
  • Bekreft verdien med kommandoen under.
az containerapp job show `
  -g rg-agentic-workshop `
  -n "$WORKER_JOB_NAME" `
  --query properties.configuration.eventTriggerConfig.scale.pollingInterval

Kommandoen krever separat Azure-lesetilgang. Uten den ber du kurslederen bekrefte verdien i portalen.

Hvis noe stopper

Webhooken når ikke fram

Ikke legg WEBHOOK_SECRET i terminalhistorikk eller del den i en issue. Be kurslederen kontrollere Recent deliveries og redelivere webhooken med kurslederens oppsett.

Deploy feiler på rettigheter

Kontroller at AZURE_CREDENTIALS finnes som repository secret og at AGENT_NAME er satt. Hvis feilen fortsetter, må kurslederen rette service-principalens roller.

Jobben feiler med en gang

Hvis du har Azure-lesetilgang, les az containerapp job logs show; ellers be kurslederen hente loggen. Manglende miljøvariabler ligger vanligvis under env: i infra/main.bicep.
