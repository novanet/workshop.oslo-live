Det tekniske du trenger

Denne siden forklarer hvor koden bor, hvordan en issue blir til en pull request, hva modellen får lov til å gjøre, og hvor du leter når noe feiler.

SpråkC# på .NET 10.
ModellClaude Code headless via claude -p.
DriftAzure Container Apps, Storage Queue og Key Vault.

Fra issue til PR

Det er to kjøremiljøer med en tydelig grense mellom dem: Receiveren tar imot HTTP og legger en melding i kø; workeren gjør det tunge, modellerte arbeidet.

GitHub issue + etikett
        │ webhook
        ▼
Receiver (Container App, scale-to-zero)
        │ signert melding
        ▼
Storage Queue ── KEDA ──► Worker (Container Apps Job)
                              │
                              ├─ klon repo og lag branch
                              ├─ bygg systemprompt og kontekst
                              ├─ kjør claude -p med stage-profil
                              ├─ kjør dotnet build/test utenfor modellen
                              └─ push branch og åpne PR

GitHub trenger et raskt HTTP-svar. Derfor skal ikke Receiveren kjøre Claude eller git. Jobben kan bruke flere minutter uten at webhooken står åpen.

Ikke repository secretsGH_TOKEN skal ikke lages eller lagres på Secrets/agents-siden til Oslo Live. Den siden brukes til repository secrets, ikke til den lokale workeren. Lag tokenet som et personlig fine-grained token på GitHub → New fine-grained token, legg det i den lokale .env-fila, og la deploy.sh håndtere Azure-lagringen i Lab 2.

Slik lager eller får du de tre viktigste nøklene

  1. GitHub-token — lag selv: Åpne GitHub → New fine-grained token (alternativt: Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token). Gi tokenet et navn som mini-kari-workshop, velg kort utløpsdato, velg bare novanet/workshop.oslo-live under repository access, sett Contents, Issues og Pull requests til read/write og Metadata til read. SSO er bare relevant hvis GitHub viser en godkjenning. Trykk Generate token, kopier verdien med én gang til .env, og test med --dry-run.
  2. Anthropic-nøkkel — få fra kurslederen: Del en separat nøkkel per deltaker eller agent fra kursets Anthropic-workspace med kostnadstak. Nøkkelen skal bare ligge i .env lokalt og i Azure Key Vault via ./deploy.sh. Deltakeren trenger ikke egen betaling; Claude.ai-abonnement er ikke det samme som API-kreditt.
  3. Webhook-hemmelighet — få fra kurslederen: Be om den felles WEBHOOK_SECRET-verdien etter at du har deployet. Kurslederen kobler mottaks-URL-en din til Oslo Live og bruker samme hemmelighet på GitHub-webhooken. Ved et helt eget oppsett lager du den selv med openssl rand -hex 32.
Hvis GitHub-operasjoner feilerLogger workeren addComment eller replaceActorsForAssignable når tokenet gjelder feil repo eller mangler Issues write. Kontroller repository access før du leter etter SSO; det er normalt å ikke se en SSO-knapp. gh auth login og GH_TOKEN er separate innlogginger; workeren bruker tokenet i den lokale .env-fila.
Hvis Claude-nøkkelen manglerLogger workeren Mangler eller ikke utfylt: ANTHROPIC_API_KEY og avslutter før Claude Code starter. Be kurslederen om nøkkelen. Hvis Anthropic Console viser Payment failed, skal deltakeren bruke kursnøkkelen i stedet. --dry-run kan brukes uten denne nøkkelen.
Behandle disse som passordIkke commit .env, lim nøkler inn i issue eller PR, legg dem i JavaScript, eller send dem i chat. Hvis en nøkkel lekker: si fra med en gang, tilbakekall den i leverandørens portal, og få en ny.

Logg inn i verktøyene

# GitHub CLI – brukes når du oppretter agentrepoet
gh auth login
gh auth status

# Azure CLI – kurslederen gir deg brukeren og subscription-tilgangen
az login --use-device-code
az account show
az account list -o table

gh auth login er innloggingen for din egen GitHub-konto og brukes til å opprette det private agentrepoet. GH_TOKEN er tokenet workeren bruker mot novanet/workshop.oslo-live; de to tilgangene kan være forskjellige. For Azure logger du inn med kurskontoen du har fått, og velger riktig subscription hvis du har flere.

Verdier du ikke skal fylle inn selv

Deployen lager resten og legger hemmelighetene i Key Vault. Du trenger ikke finne eller kopiere disse inn i .env:

VerdiHvor den kommer fraHva du gjør
QUEUE_CONNECTIONStorage-kontoen som Bicep oppretter.La deploy.sh og Azure håndtere den.
MEMORY_CONNECTIONSamme Storage-konto; brukes til bloben hukommelse/memory.md.Ikke legg connection string i repoet.
QUEUE_NAMESettes av Bicep til agent-tasks.Ikke endre den uten å endre både mottak og worker.
Key Vault-hemmeligheter./deploy.sh skriver API-nøkkel, GitHub-token og webhook-hemmelighet til Key Vault.Bruk managed identity; ikke kopier verdiene inn i Bicep eller containerbildet.
AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_IDDette er kurslederens GitHub Actions-/infrastrukturverdier, ikke deltakerens lokale oppsett.Ikke be om eller legg dem i agentrepoet. Deltakeren logger inn med az login --use-device-code.

Mappene som betyr noe

src/Worker/

Pipeline.cs er orkestreringen deltakerne implementerer i Lab 1. Repository.cs håndterer klon, branch, commit og PR. ClaudeRunner.cs kjører modellen.

src/Receiver/

En liten ASP.NET Core-app som validerer webhooken og skriver til køen. Den har ingen LLM og ingen git.

agent/

system.md, conventions.md, prompts, skills, stages og hukommelse styrer modellens oppførsel.

infra/

main.bicep beskriver Container Apps, jobben, køen, Key Vault, identitet og miljøvariabler.

deploy.sh

Deployer infrastrukturen, bygger bildene i ACR og ruller ut den nye revisjonen.

.env

Lokale hemmeligheter og navn. Filen skal aldri committes eller legges i issue, PR eller logg.

Hva som er kode og hva som er modell

Deterministisk kode

Reservasjon, arbeidsområde, promptbygging, diff-sjekk, bygg/test, commit, push og PR. Disse delene skal gi samme kontroll ved hver kjøring.

Modellens arbeid

Les oppgaven, finn relevant kode, velg en implementasjon og gjør endringer innenfor verktøyprofilen. Modellen avgjør ikke om leveransen er grønn.

Kvalitetsportene

En tom diff stopper leveransen. Bygg eller test kjøres etter modellsteget. Rødt bygg gir PR som utkast og skal ikke merges automatisk.

Stages og verktøytilgang

agent/stages.json er arbeidsflytens kontrollpanel. Hver stage kan ha egen prompt, modell, verktøyliste, maks antall turer og timeout.

StageTypisk tilgangHvorfor
ResearchRead, Glob, GrepForstå oppgaven uten å endre kode.
ImplementLesing, Edit, Write, bygg og testGjøre endringen og kontrollere lokalt.
Self-reviewLesing, diff og test; helst ikke fri skrivingFinne feil før leveranse uten å omskrive alt.

Minst mulig tilgang er et teknisk valg. Fjerner du Write, kan agenten fortsatt gjøre mye med Edit. Legger du til et bredt Bash-mønster, øker konsekvensen av en feil instruksjon.

Vil du bygge en monitoreringsside i Lab 3, kan nettleseren lese det offentlige GitHub API-et for issues og pull requests. Den kan vise statuser, lenker og forbrukstabellen i PR-kroppen. Azure-logger og hemmeligheter skal ikke hentes direkte fra JavaScript; bruk en innlogget backend eller lenk til Azure-portalen.

Tre kvalitetsporter du må kunne forklare

  1. Reservasjon: et kontrollpunkt som stopper to agenter fra å bruke tokens på samme issue.
  2. Verktøyprofil: et kontrollpunkt som begrenser hva modellen kan lese, skrive og kjøre.
  3. Bygg/test: et kontrollpunkt som avgjør med faktisk kode om resultatet kan leveres.
Modellen er ikke en sikkerhetsgrense aleneIssues og kommentarer er brukerstyrt data. Branch protection, token-rettigheter, verktøyallowlist og deterministiske kvalitetsporter må sammen beskytte leveransen.

Kommandoer du bruker oftest

# lokalt
dotnet build --nologo -v quiet
dotnet run --project src/Worker -- --issue 1 --repo novanet/workshop.oslo-live --skip-reservation
dotnet run --project src/Worker -- --issue 1 --repo novanet/workshop.oslo-live --dry-run

# Azure
./deploy.sh
az containerapp job execution list -g $RESOURCE_GROUP -n caj-$NAME-worker -o table
az containerapp job logs show -g $RESOURCE_GROUP -n caj-$NAME-worker --container worker --follow

# målrepo
gh issue list --repo novanet/workshop.oslo-live
gh pr list --repo novanet/workshop.oslo-live

--dry-run sjekker issue og reservasjon uten å reservere, klone, kommentere eller starte Claude Code. Det krever --issue og --repo, og skal ikke brukes mot kømodus.

Når noe feiler

Bygget feiler

Les første egentlige compiler-feil, rett én ting, og kjør dotnet build igjen. Ikke be modellen om å rapportere grønt.

Ingen PR

Se etter tom diff, rødt bygg eller stage-feil i workeren. Se også at GH_TOKEN har tilgang til målrepoet.

Azure-jobben starter ikke

Sjekk etiketten, webhook delivery, queue og KEDA. Deretter les jobbloggen; manglende miljøvariabler står ofte under env: i Bicep.

PR-en er dyr

Les LLM request completed-linjene. Reduser kontekst, modell eller maxTurns én endring om gangen.
