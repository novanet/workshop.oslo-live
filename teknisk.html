Det tekniske du trenger

Denne siden forklarer hvor koden bor, hvordan en issue blir til en pull request, hva modellen får lov til å gjøre, og hvor du leter når noe feiler.

SpråkC# på .NET 10.
ModellClaude Code headless via claude -p.
DriftAzure Container Apps, Storage Queue og GitHub Actions secrets.

Fra issue til PR

Det er to kjøremiljøer med en tydelig grense mellom dem: Receiveren tar imot HTTP og legger en melding i kø; workeren gjør det tunge, modellerte arbeidet.

GitHub issue + etikett ─┐
GitHub PR + @mention   ───┤ webhook
        ▼
Receiver (Container App, scale-to-zero)
        │ signert melding
        ▼
Storage Queue ── KEDA ──► Worker (Container Apps Job)
                              │
                              ├─ klon repo og lag branch
                              ├─ bygg systemprompt og kontekst
                              ├─ kjør claude -p med stage-profil
                              ├─ kjør dotnet build/test utenfor modellen
                              └─ push branch og åpne PR

GitHub trenger et raskt HTTP-svar. Derfor skal ikke Receiveren kjøre Claude eller git. Jobben kan bruke flere minutter uten at webhooken står åpen.

Webhooken abonnerer på issues for nye oppgaver og, når AGENT_MENTION er satt, på issue_comment, pull_request_review_comment og pull_request_review. En PR-mention legges i samme kø, men workeren sjekker PR-en read-only og svarer uten å opprette branch eller PR. Inline review-kommentarer bruker GitHub-reply-endepunktet og blir i samme tråd; vanlige PR-kommentarer får et nytt toppnivå-svar.

KEDA og jq i Lab 2

KEDA er skaleringskomponenten

KEDA betyr Kubernetes Event-driven Autoscaling. I Azure Container Apps overvåker den Storage Queue og starter Container Apps Job når køen har meldinger. minExecutions: 0 gir scale-to-zero, pollingInterval: 30 bestemmer hvor ofte køen sjekkes, og maxExecutions: 3 setter en øvre grense for kjøringer.

jq er JSON-leseren

GitHub Actions skriver Azure-output til .deploy-outputs.json. Kommandoen jq -r .receiverUrl.value .deploy-outputs.json henter mottaks-URL-en fra JSON-filen slik at den kan brukes i curl. Den gjør ingen endring i Azure.

Normal flytWebhooken treffer Receiveren, Receiveren legger én melding i køen, KEDA oppdager meldingen og starter en job execution, og workeren henter meldingen og avslutter. En forsinkelse på opptil polling-intervallet er forventet.

Slik lager eller får du de tre viktigste nøklene

  1. GitHub-token — lag selv: Åpne GitHub → New fine-grained token (alternativt: Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token). Gi tokenet et navn som mini-kari-workshop, velg kort utløpsdato, velg bare novanet/workshop.oslo-live under repository access, sett Contents, Issues og Pull requests til read/write og Metadata til read. SSO er bare relevant hvis GitHub viser en godkjenning. Trykk Generate token, kopier verdien til .env for Lab 1, og legg den også som repository secret GH_TOKEN for Lab 2.
  2. Anthropic-nøkkel — få fra kurslederen: Del en separat nøkkel per deltaker eller agent fra kursets Anthropic-workspace med kostnadstak. Legg den i lokal .env for Lab 1 og som repository secret ANTHROPIC_API_KEY for Lab 2. Deltakeren trenger ikke egen betaling; Claude.ai-abonnement er ikke det samme som API-kreditt.
  3. Webhook-hemmelighet — få fra kurslederen: Legg WEBHOOK_SECRET som repository secret og bruk samme verdi på GitHub-webhooken når mottaks-URL-en din er klar.
Hvis GitHub-operasjoner feilerLogger workeren addComment eller replaceActorsForAssignable når tokenet gjelder feil repo eller mangler Issues write. Kontroller repository access før du leter etter SSO; det er normalt å ikke se en SSO-knapp. gh auth login og GH_TOKEN er separate innlogginger; workeren bruker tokenet i den lokale .env-fila.
Hvis Claude-nøkkelen mangler eller mangler workspaceLogger workeren Mangler eller ikke utfylt: ANTHROPIC_API_KEY hvis nøkkelen mangler. Den nyeste workeren bruker kursets workspace-ID automatisk når .env mangler den. Hvis feilen fortsatt vises, hent nyeste mini-nils.zip og kontroller oppstartloggen for Anthropic workspace-ID: satt. --dry-run kan brukes uten denne nøkkelen.
Behandle disse som passordIkke commit .env, lim nøkler inn i issue eller PR, legg dem i JavaScript, eller send dem i chat. Hvis en nøkkel lekker: si fra med en gang, tilbakekall den i leverandørens portal, og få en ny.

Verdier du ikke skal fylle inn selv

GitHub Actions lager resten. Workflowen sender repository secrets til Bicep som secure parametere. Du trenger ikke finne eller kopiere disse inn i .env for Azure:

VerdiHvor den kommer fraHva du gjør
QUEUE_CONNECTIONStorage-kontoen som Bicep oppretter.La workflowen og Azure håndtere den.
MEMORY_CONNECTIONSamme Storage-konto; brukes til bloben hukommelse/memory.md.Ikke legg connection string i repoet.
QUEUE_NAMESettes av Bicep til agent-tasks.Ikke endre den uten å endre både mottak og worker.
Repository secretsGH_TOKEN, ANTHROPIC_API_KEY, WEBHOOK_SECRET og AZURE_CREDENTIALS.Kun ved Actions-oppsett. Legg dem inn i deltakerrepoet. De sendes secure til deployen og skal ikke legges i image eller ACR.
AGENT_NAMEAgentidentitet for workflowen.Sett som repository variable. Lokal deploy er deaktivert.

Lokale hemmeligheter og navn. Filen skal aldri committes eller legges i issue, PR eller logg.

Hva som er kode og hva som er modell

Deterministisk kode

Reservasjon, arbeidsområde, promptbygging, diff-sjekk, bygg/test, commit, push og PR. Disse delene skal gi samme kontroll ved hver kjøring.

Modellens arbeid

Les oppgaven, finn relevant kode, velg en implementasjon og gjør endringer innenfor verktøyprofilen. Modellen avgjør ikke om leveransen er grønn.

Kvalitetsportene

En tom diff stopper leveransen. Bygg eller test kjøres etter modellsteget. Rødt bygg gir PR som utkast og skal ikke merges automatisk.

Stages og verktøytilgang

agent/stages.json er arbeidsflytens kontrollpanel. Hver stage kan ha egen prompt, modell, verktøyliste, maks antall turer og timeout.

StageTypisk tilgangHvorfor
Researchclaude-opus-5; Read, Glob, GrepForstå oppgaven og skrive en plan uten å endre kode.
Plan reviewclaude-haiku-4.5; lesingFinne hull i planen billig; alt annet enn PLAN GODKJENT stopper kjøringen.
Implementclaude-fable-5; lesing, Edit, Write, bygg og testGjøre endringen etter planen.
Self-reviewclaude-opus-5; lesing, diff, Edit og testFinne og rette feil før den deterministiske leveransen.
Build & deliverDeterministisk kodeBygg, test, commit, push og PR uten modellskjønn.

GPT-modellene i noen sammenlignbare pipeline-tegninger kan ikke settes direkte inn her: denne starterkoden bruker claude -p og Anthropic-modeller. Modellvalget er likevel en eksplisitt stage-konfigurasjon i agent/stages.json. Her bruker vi modell-ID-er som må være tilgjengelige for kursnøkkelen, med claude-fable-5 som standard.

Minst mulig tilgang er et teknisk valg. Fjerner du Write, kan agenten fortsatt gjøre mye med Edit. Legger du til et bredt Bash-mønster, øker konsekvensen av en feil instruksjon.

Tre kvalitetsporter du må kunne forklare

  1. Issue-status: et kontrollpunkt som stopper arbeid på lukkede issuer; flere agenter kan konkurrere på en åpen issue, og første mergete PR vinner.
  2. Verktøyprofil: et kontrollpunkt som begrenser hva modellen kan lese, skrive og kjøre.
  3. Bygg/test: et kontrollpunkt som avgjør med faktisk kode om resultatet kan leveres.
Modellen er ikke en sikkerhetsgrense aleneIssues og kommentarer er brukerstyrt data. Branch protection, token-rettigheter, verktøyallowlist og deterministiske kvalitetsporter må sammen beskytte leveransen.

--dry-run sjekker issue-status uten å reservere, klone, kommentere eller starte Claude Code. Direkte issue-kjøring uten --dry-run er blokkert i starter-kitet. Det krever --issue og --repo, og skal ikke brukes mot kømodus; levering skal skje fra Azure etter webhook-triggeren.

Når noe feiler

Bygget feiler

Les første egentlige compiler-feil, rett én ting, og kjør dotnet build igjen. Ikke be modellen om å rapportere grønt.

Ingen PR

Kontroller først at webhook, kø og Azure-jobb kjørte. Deretter se etter tom diff, rødt bygg eller stage-feil. GH_TOKEN trenger write-tilgang i Lab 2 fordi agenten skal tildele issue, kommentere og opprette PR.

Azure-jobben starter ikke

Sjekk etiketten, webhook delivery, Storage Queue og KEDA. KEDA kan bruke opptil polling-intervallet på å oppdage meldingen. Deretter les jobbloggen; manglende miljøvariabler står ofte under env: i Bicep.

PR-en er dyr

Les LLM request completed-linjene. Reduser kontekst, modell eller maxTurns én endring om gangen.
