Det tekniske du trenger

Denne siden forklarer hvor koden bor, hvordan en issue blir til en pull request, hva modellen får lov til å gjøre, og hvor du leter når noe feiler.

SpråkC# på .NET 10.
ModellClaude Code headless via claude -p.
DriftAzure Container Apps, Storage Queue og GitHub Actions secrets.

Fra issue til PR

Det er to kjøremiljøer med en tydelig grense mellom dem: Receiveren tar imot HTTP og legger en melding i kø; workeren gjør det tunge, modellerte arbeidet.

GitHub issue + etikett
        │ webhook (signert med HMAC)
        ▼
Receiver (Container App, minReplicas 1)
        │ kømelding (ikke signert)
        ▼
Storage Queue ── KEDA ──► Worker (Container Apps Job, scale-to-zero)
                              │
                              ├─ klon repo og lag branch
                              ├─ bygg systemprompt og kontekst
                              ├─ kjør claude -p med stage-profil
                              ├─ kjør dotnet build/test utenfor modellen
                              └─ push branch og åpne PR

GitHub venter maks 10 sekunder på svar fra webhooken. Derfor kjører ikke Receiveren Claude eller git. Den sjekker signaturen, legger én melding i køen og svarer med en gang. Under kurset har Receiveren minReplicas: 1, så den svarer raskt uten kaldstart. Workeren skalerer fortsatt til null og kan bruke flere minutter uten at webhooken står åpen.

Bare webhooken er signert. Kømeldingen er ikke signert; det er tilgangen til Storage-kontoen som beskytter køen. Både Receiveren og workeren avviser issues fra andre repoer enn TARGET_REPO.

KEDA og Actions Summary i Lab 2

KEDA er skaleringskomponenten

KEDA betyr Kubernetes Event-driven Autoscaling. I Azure Container Apps overvåker den Storage Queue og starter Container Apps Job når køen har meldinger. minExecutions: 0 gir scale-to-zero, pollingInterval: 30 bestemmer hvor ofte køen sjekkes, og maxExecutions: 3 setter en øvre grense for kjøringer.

Actions Summary viser navnene

Når deployen er ferdig, står verdiene du trenger nederst på workflow-kjøringen i GitHub Actions: Receiver URL, Receiver, Worker job, Issue label, Azure suffix og Resource group. Fila .deploy-outputs.json finnes bare på Actions-runneren, ikke hos deg.

Normal flytWebhooken treffer Receiveren, Receiveren legger én melding i køen, KEDA oppdager meldingen og starter en job execution, og workeren henter meldingen og avslutter. En forsinkelse på opptil polling-intervallet er forventet.

Slik lager eller får du nøklene

  1. GitHub-token, lag selv: Godta først collaborator-invitasjonen til novanet/workshop.oslo-live. Åpne så GitHub → New personal access token (classic) (alternativt: Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token (classic)). Gi tokenet et navn som mini-kari-workshop, velg kort utløpsdato og kryss bare av public_repo. Ikke velg hele repo. Fine-grained funker ikke for collaborators utenfor Novanet-orgen. Trykk Generate token, kopier verdien til .env for Lab 1, og legg den som repository secret GH_TOKEN.
  2. Anthropic-nøkkel, få fra kurslederen: Hele kurset deler én nøkkel med ett felles kostnadstak. Legg den som repository secret ANTHROPIC_API_KEY. Du trenger den ikke lokalt.
  3. Webhook-hemmelighet, få fra kurslederen: Legg den som repository secret WEBHOOK_SECRET. Kurslederen registrerer samme verdi på webhooken din.
  4. Azure-credentials, få fra kurslederen: Legg hele JSON-en som repository secret AZURE_CREDENTIALS. Den gir Contributor på den delte ressursgruppen, så den skal bare brukes av GitHub Actions.

Hva som er kode og hva som er modell

Deterministisk kode

Reservasjon, arbeidsområde, promptbygging, diff-sjekk, bygg/test, commit, push og PR. Disse delene skal gi samme kontroll ved hver kjøring.

Modellens arbeid

Les oppgaven, finn relevant kode, velg en implementasjon og gjør endringer innenfor verktøyprofilen. Modellen avgjør ikke om leveransen er grønn.

Kvalitetsportene

Plan-review må svare PLAN GODKJENT, ellers stopper kjøringen. En tom diff stopper leveransen. Bygg og test kjøres etter modellstegene. Rødt bygg gir PR som utkast, eller ingen PR når stopOnVerifyFailure er true. Auto-merge er av; et menneske merger.

Stages og verktøytilgang

agent/stages.json er arbeidsflytens kontrollpanel. Pipelinen er fire steg + levering: fire modellsteg, og så levering som er kode. Hver stage kan ha egen prompt, modell, verktøyliste, maks antall turer og timeout.

StageTypisk tilgangHvorfor
Researchclaude-opus-5-5; Read, Glob, GrepForstå oppgaven og skrive en plan uten å endre kode.
Plan-reviewclaude-haiku-4-5; lesingFinne hull i planen billig; alt annet enn et svar som starter med PLAN GODKJENT stopper kjøringen.
Implementclaude-sonnet-5; lesing, Edit, Write, bygg og testGjøre endringen etter planen.
Self-reviewclaude-sonnet-5; lesing, diff, Edit og testFinne og rette feil før leveringen.
LeveringKode, ikke modellBygg, test, commit, push og PR uten modellskjønn.

Toppnivå "model" i stages.json er claude-sonnet-5 og gjelder stages uten egen model. I Azure setter deployen alltid CLAUDE_MODEL (standard claude-sonnet-5), og den overstyrer toppnivå-verdien, men ikke stages med egen modell. Priser per million tokens, input/output: claude-opus-5-5 $4/$20, claude-sonnet-5 $2/$10, claude-haiku-4-5 $1/$5.

Minst mulig tilgang er et teknisk valg. Fjerner du Write, kan agenten fortsatt gjøre mye med Edit. Legger du til et bredt Bash-mønster, øker konsekvensen av en feil instruksjon.

Ekstra: mention-modus (eksperimentelt)

Labbene bruker ikke mention-modus. Vil du prøve etter kurset, setter du repository variable AGENT_MENTION til GitHub-loginet som eier GH_TOKEN, uten @. Da registreres webhooken også for PR-kommentarer og review-tråder, og agenten svarer read-only på en PR uten å lage branch eller ny PR.

  • Noen andre enn deg må skrive mentionen. Agenten ignorerer sitt eget login, og den kommenterer med ditt token.
  • Bare mentions fra collaborators på repoet teller, ikke fra forks.
  • I mention-modus får agenten ingen MCP-servere.

Tre kvalitetsporter du må kunne forklare

  1. Issue-status: et kontrollpunkt som stopper arbeid på lukkede issuer; flere agenter kan konkurrere på en åpen issue, og første mergete PR vinner.
  2. Verktøyprofil: et kontrollpunkt som begrenser hva modellen kan lese, skrive og kjøre.
  3. Bygg/test: et kontrollpunkt som avgjør med faktisk kode om resultatet kan leveres.
Modellen er ikke en sikkerhetsgrense aleneIssues og kommentarer er brukerstyrt data. Branch protection, token-rettigheter, verktøyallowlist og deterministiske kvalitetsporter må sammen beskytte leveransen.

Når noe feiler

Bygget feiler

Les første egentlige compiler-feil, rett én ting, og kjør dotnet build igjen. Ikke be modellen om å rapportere grønt.

Ingen PR

Se først etter kommentarer fra agenten på issuen. Den skriver hvorfor den stoppet: plan ikke godkjent, tom diff, rødt bygg eller stage-feil. Kom det ingen kommentar, be kurslederen sjekke webhook delivery og jobbloggen. GH_TOKEN trenger public_repo fordi agenten skal tildele issue, kommentere og opprette PR.

Azure-jobben starter ikke

Sjekk at etiketten er riktig, og at Actions Summary viser samme Issue label. KEDA kan bruke opptil polling-intervallet på å oppdage meldingen. Kurslederen kan sjekke webhook delivery, køen og jobbloggen; manglende miljøvariabler står ofte under env: i Bicep.

PR-en er dyr

Les forbrukstabellen i PR-en. Den viser modell, tokens og kostnad per steg. Reduser kontekst, modell eller maxTurns én endring om gangen.
